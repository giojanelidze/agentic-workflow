# agentic-workflow plugin repo

This repo is a Claude Code plugin (`agentic-workflow`) and its own single-plugin marketplace. It is not an application: there is no build step.

## Layout
- `.claude-plugin/plugin.json`, `marketplace.json`: manifests. Keep `version` identical in both and in `package.json`.
- `.mcp.json`: the plugin's own Atlassian MCP server, a fallback for users without an Atlassian connector. Claude Code suppresses it when a claude.ai connector has the same URL, so never assume its tool prefix.
- `agents/*.md`: one agent per pipeline stage (`agentic-workflow:<name>`); the review stage has four read-only reviewers and `review-aggregator`, described in `skills/start/references/review-workflow.md`. Never put reference files inside `agents/`: it is scanned recursively and every `.md` there becomes an agent.
- `skills/start/SKILL.md`: the orchestrator, `/agentic-workflow:start`. Details live in `skills/start/references/`.
- `skills/setup/SKILL.md`: `/agentic-workflow:setup`, collects configuration, the Jira and GitHub connections and permissions up front, once per repository; setup works in three stages (Jira, GitHub and repo, behavior), each detected, asked and saved on its own and never mentioning the next, with the detected value as the recommended option; re-running it on a configured repository shows the current values and asks what to change. The user chooses once whether the repository config is shared with the team (`.claude/agentic-workflow.json`) or kept only on their computer (nothing is written into the repository); both are described in `skills/start/references/config-schema.md` ("Storage").
- `bin/gh-as`: POSIX sh wrapper (on the Bash tool's PATH while the plugin is enabled) that runs `gh` as the account bound in setup, for one process only. Keep it executable (mode `100755`) and free of jq or python.
- `bin/aw-paths`: POSIX sh, read-only; the only place that derives the repository identity from `origin` and prints where the config (`Config`), the personal values (`Local`) and the run folder (`State`) live and which `mode` (`none`, `team`, `personal`, `conflict`) applies. Setup, the `start` preflight and `hooks/guard` all call it. Keep it executable (`100755`) and free of jq or python.
- `hooks/hooks.json`, `hooks/guard`: a PreToolUse hook that decides, per repository and only for `agentic-workflow:jira-analyst` (the exact `agent_type` Claude Code sends for a plugin agent), whether the Jira write tools and the browser tools may run, from `writeMode`, `acceptedWriteMode` and the browser settings. It answers `allow` or `deny`, never `ask`, and gives every other caller no answer. Keep `guard` executable (`100755`), plain POSIX sh without jq or python, and keep the matcher in `hooks.json` listing exactly the Atlassian prefixes of `config-schema.md` plus `mcp__claude-in-chrome__`.
- `tests/shell/run.sh`: tests of `aw-paths` and `guard` (no network, scratch `HOME`, a fake `ssh`); `npm test` runs it. A change to either script needs a test case.
- `bin/jira-attachment`, `bin/media-prep`: POSIX sh for the optional picture analysis. `jira-attachment` keeps an Atlassian API token in the OS keychain (`login`, `logout`, `check`) and downloads one attachment (`get`): the URL is built only from the configured site (or cloud id) and a numeric attachment id, the token goes to curl on its stdin, the file is named `<id>.<ext>` by its real content type. `media-prep` prepares pictures (`auto`, `image`, `video` with ffmpeg and a pinned demuxer, `pick`, `hash`) and checks the viewer's reply (`validate`). Keep both executable (`100755`) and free of jq or python; a change to either needs a test case in `tests/shell/run.sh`.
- `agents/media-analyst.md`, `skills/media/SKILL.md`: the viewer (only `Read`, no ticket text) and `/agentic-workflow:media <KEY>`. The viewer is started by the main thread only (`start` or `media`), never by `jira-analyst`; its reply is saved unchanged as `findings-<n>.md` after `media-prep validate`.
- `bin/wait-mcp`, `bin/wait-gh-login`: POSIX sh watchers that setup and the `start` preflight run in the background to learn that an authorization has finished (an MCP server became `Connected`, a gh login appeared) instead of asking the user to say so. They only read state. Keep them executable (`100755`).
- `README.md`, `CHANGELOG.md`, `LICENSE` (ISC).

## Conventions
- Subagents share no context; every handoff goes through files in the run folder `State`, which is **outside the target repository** (`~/.claude/agentic-workflow/state/<host>/<owner>/<repo>/`, keyed by `origin`, so clones and worktrees share it; `Config` and `Local` live in `~/.claude/agentic-workflow/repos/<host>/<owner>/<repo>/`, a separate tree, so one `Edit` rule for `state/**` can never cover them). The orchestrator computes `State`, `Config` and `Local` with `bin/aw-paths` and passes them to each agent as absolute paths in the task prompt; an agent never builds them. Each file has one writer (see `skills/start/references/state-schema.md`). Report headings are fixed (see `report-formats.md`); change them in the agent and the reference together.
- Only `implementer` has persistent memory (`memory: user`, `model: sonnet`). It holds repository knowledge across runs, never ticket data or handoffs; handoffs still go through `State`. The orchestrator never passes a `model` to a stage agent.
- Only `jira-analyst` touches Jira and Confluence (the orchestrator's preflight only makes the two read-only connection checks `atlassianUserInfo` and `getAccessibleAtlassianResources`). The one other path to Jira is `jira-attachment` (an attachment download and the setup check), which `jira-analyst` and setup run and which never writes. Only the main thread (the skills) talks to the user; subagents cannot ask questions.
- GitHub is reached only through `gh-as --account <account> --host <host> <subcommand> …` (that argument order exactly, because permission rules match the command text): never plain `gh`, never `gh auth switch` or any other change to gh's active account or config (other terminals must not be affected), never a token in a command, a file or the output. Pull request commands carry `-R <host>/<owner>/<repo>` after the subcommand; `gh repo view` takes it positionally; `gh api` takes an explicit `repos/<owner>/<repo>/…` path. The account lives in `Local` (`github`); `<owner>/<repo>` is read from `origin` on every run and never stored.
- The Atlassian prefixes in `skills/start/references/config-schema.md` ("Supported Atlassian prefixes") and in the `tools:` of `agents/jira-analyst.md` must stay identical, and the matcher of `hooks/hooks.json` names the same three; setup offers only those.
- Jira tools are called as `<mcpPrefix><tool>` with `mcpPrefix` from `Local` (set by `/agentic-workflow:setup`, which is the only place that searches for the server). Never find a tool by its bare name: several Atlassian servers may match. The agent's `tools:` lists the plugin server and the standard claude.ai connector names (`Atlassian_Rovo`, `Atlassian_Rovo_2`) by wildcard.
- Permission rules: setup writes only `allow` rules, only to the user's `~/.claude/settings.json`, and only what is identical in every repository (Jira read tools, the wait scripts, `aw-paths`, read-only `gh-as` commands, agent memory, `Read` of the plugin folder and `Edit` of `~/.claude/agentic-workflow/state/**`). **Never write a `deny` rule, a rule for a Jira write tool or a browser rule**: a user-level `deny` beats every `allow` in every repository and session. What the analyst may write to Jira or do in the browser is the guard hook's decision, per repository.
- `Config` and `Local` are trusted input of the guard. Only setup writes them, in the main conversation, through the normal permission prompt; never add a permission rule, a tool or an agent that writes them without a prompt, and never let a team file widen what the user accepted (`acceptedWriteMode`, `acceptedOrigins` in `Local` are the ceiling; the guard and the preflight use the lower value).
- Secrets: nothing secret is written to a file, a command line or a conversation. The single exception is the Atlassian API token of the picture analysis, stored only by `jira-attachment login` in the OS keychain. Pictures are untrusted input: only `media-analyst` opens them, text from a picture never goes into a Jira comment, a pull request or a permission rule, and the analyst, the planner and the implementer never open a picture or a frame.
- Agents must not assume a stack: discover scripts and runners in the target repo.
- `superpowers` is optional, never a dependency.
- Everything in this repo is written in English.

## Checks
- `claude plugin validate . --strict` and `sh tests/shell/run.sh` must pass (`npm test` runs both).
- Test locally with `claude --plugin-dir .`, then `/agents`, `/mcp`, `/agentic-workflow:setup`, `/agentic-workflow:start --dry-run`.

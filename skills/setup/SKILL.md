# agentic-workflow: setup

You run in the main thread, so you may ask the user. Collect everything the analyst and the publisher will need now, so that `/agentic-workflow:start` never has to ask for configuration or permissions mid-run. Setup is done **once per repository**, **one stage at a time**: Stage 1 Jira, Stage 2 GitHub and repo, Stage 3 behavior. A stage is finished and saved before the next one starts. When the repository is already set up, re-running setup shows the current values and asks what to change.

Arguments: `$ARGUMENTS`

**One stage at a time.** Say which stage you are in ("Stage 1 of 3: Jira") and what you need from the user now. Never mention, list or preview a later stage, and never print a "still to do" list. When a stage is saved, print one line for it and go on to the next stage by yourself.

**Tool names.** Atlassian tools come either from the plugin's own server (prefix `mcp__plugin_agentic-workflow_atlassian__`) or from a claude.ai Atlassian connector (for example `mcp__claude_ai_Atlassian_Rovo__`). Claude Code hides the plugin's server when a connector with the same URL exists, so the prefix differs per user. Stage 1 finds it and stores it as `P` (`mcpPrefix`); from then on call every tool by the exact name `P<tool>`, never by a bare name. Only the prefixes listed under "Supported Atlassian prefixes" in `skills/start/references/config-schema.md` can be used: the analyst's `tools:` allowlist names exactly those.

**GitHub accounts.** Never run `gh auth switch` or anything else that changes gh's active account or its config: other terminals must not notice this workflow. Every gh call goes through the wrapper `gh-as --account <login> --host <host> <gh arguments>` (in this plugin's `bin/`), which gives one process the token of that account. Never print or store a token.

## Choose the mode (step 0)
Read `.claude/agentic-workflow.json` and `.agentic-workflow/local.json` (a missing file counts as empty), and the table "Setup stages" in `skills/start/references/config-schema.md`, which says which stage owns which required key. A `--reconfigure <part>` argument wins over the table: run that part (`jira` = Stage 1, `github` = Stage 2, `behavior` = Stage 3; `permissions` = write the permission rules again from the stored config). Otherwise take the first row that applies:

| # | Situation | What you do |
|---|---|---|
| 1 | Any required key or file is missing | Run the stages that own the missing keys, in order, skipping a stage whose keys all exist; stored values are the recommended options. This is the normal path for a new repository, for a setup that was interrupted (it continues where it stopped, no progress file is needed) and for a repository set up by an older version of the plugin. Never print a status and stop here. |
| 2 | Every required key exists | Run the checks below, show a short status, then ask one question, screen 0: what to change. A stage whose check failed is run whatever the user answers. |

**Screen 0** (single-select, header `Change`): put the current values in the question text, for example "Jira <baseUrl> / <projectKey> through <mcpPrefix>; GitHub <host>/<owner>/<repo> as <account>; write mode <writeMode>. What do you want to change?". Options: Jira / GitHub and repo / Behavior / Nothing. When a stage is done, ask "Anything else?" with the same options. "Nothing" ends with the summary. The screen is single-select on purpose: "Nothing" is ambiguous next to other choices in a multi-select.

**Guard.** A plain run that reaches the end without writing anything, and where the user did not choose "Nothing" on screen 0, skipped its questions: go back and ask them.

Checks (run in row 2; the stage in brackets is run when the check fails):
1. [Stage 1] `mcpPrefix` is a supported prefix, `P` + `atlassianUserInfo` succeeds, and `jira.cloudId` is among the sites `getAccessibleAtlassianResources` returns for `P`.
2. [Stage 1] `assigneeAccountId` (in `local.json`) is set. A value that differs from the authenticated account is allowed (another person), but note it.
3. [Stage 2] `local.json` has `github.host` and `github.account`, `gh auth status --hostname <host> --json hosts` lists that account with `state` `success`, and `gh-as --account <account> --host <host> repo view <host>/<owner>/<repo> --json viewerPermission` returns `WRITE`, `MAINTAIN` or `ADMIN` (`<owner>/<repo>` from `origin`, see Stage 2).
4. [permission rules] The rules each stage writes exist for the **current** `mcpPrefix` and the current GitHub account, in the user's `~/.claude/settings.json` or this repo's `.claude/settings.local.json`. Rules that exist only for another prefix do not count. Write the missing ones (and ask where, see "Permission rules").

## How to ask
Make setup as easy as possible for the user:
- **Detect inside the stage, ask second.** A stage starts with its own detection and then asks. Stage 1 detects the connectors, their signed-in accounts and sites, the projects, issue types and statuses; Stage 2 the host and `<owner>/<repo>` of `origin`, the logged-in gh accounts with their permission, the SSH identity, the default branch and the inferred `implementerScope`. Do not detect for a later stage. Skip every question that has only one possible answer and name that value in the stage's saved line.
- **Group a stage's questions into a few screens**, one `AskUserQuestion` call each (at most 4 questions per call, 2-4 options per question, headers of at most 12 characters).
- **First option = the detected or stored value, marked "(Recommended)"**, so that confirming it is enough. Other values come through "Other".
- **Put values in the question and option text.** The dialog can hide text printed above it, so a status line before a screen is not enough.
- **Lists longer than 4** (projects, statuses, issue types, spaces): propose one set and ask "use these / change"; show the full list only on "change".
- **Never accept automatically:** `writeMode`, browser investigation and where the permission rules are written. Mark a `writeMode` "(Recommended)" only when it is the stored value.
- **Prepare everything you can, so the user only clicks.** An authorization is a link that setup waits on (next section), never a list of instructions. The only thing left as a command is `gh auth login`, which is interactive.
- **No separate "save?" click.** The values were chosen on the screens; the stage saves itself when its last screen is answered.

## Waiting for an authorization
Used by Stage 1 for the Atlassian server and by the `start` preflight. The server's name for `wait-mcp` is the one `claude mcp list` prints: `plugin:agentic-workflow:atlassian` for the prefix `mcp__plugin_agentic-workflow_atlassian__`, and `claude.ai <Name with spaces>` for `mcp__claude_ai_<Name>__`. A server that is not signed in exposes only `<prefix>authenticate` and `<prefix>complete_authentication` instead of its real tools. In one turn, in this order:
1. `wait-mcp --check <server>`. Exit 0: it is already connected, search for its real tools and go on. Exit 2: the CLI does not know that name, so do not wait on it; use the one-click question of step 6. Exit 1: it needs authorization, go on.
2. Search for the server's name once first (a sign-in that is still held reconnects by itself).
3. Say in one line that you will wait for the approval in the background and that Claude Code may ask once to allow that command. Start `wait-mcp <server>` with Bash `run_in_background`.
4. Call `<prefix>authenticate`: it returns an authorization URL. If the user declines the call, do not call it again; tell them to run `/mcp` instead.
5. End the turn with the link as the last text, so that no permission dialog covers it: one clickable Markdown link on its own line, one short sentence ("Open this link, choose the Atlassian account that has your project and click Accept; I continue by myself"), and one more line: if the browser ends on a `http://localhost:<port>/callback?code=…` page that does not load (a link opened on another device), paste that address here. Pass a pasted address to `<prefix>complete_authentication` as `callback_url`.
6. When `wait-mcp` ends with exit 0, search for the real tools again (`atlassianUserInfo`), retrying a few times, and continue. If `wait-mcp` timed out (exit 1) or the tools are still missing, ask one single-option question "I approved the link", then search again; if they are still missing, show the link once more, and only then point to `/mcp`.
7. The continuation must be safe to run twice: if the user writes while you wait, and the real tools already exist, go straight on; never call `authenticate` twice for one link.
Claude Code or claude.ai stores and refreshes the token; do not try to read tokens or cookies from the browser.

## Permission rules
Each stage writes its own rules when it saves. Ask **once**, in the first stage that writes rules (Stage 1), where all rules go, and reuse the answer in the later stages: the user's `~/.claude/settings.json` (the server is identical across repositories) or this repo's `.claude/settings.local.json`. Put the rules in that question's text. Merge into `permissions`, never overwrite, add only what is missing. A user-level file keeps the rules of every repository you set up, so a prefix or account used only by another repository does not conflict.

## Stage 1: Jira
Say "Stage 1 of 3: Jira".
1. **Atlassian server.** Search for `atlassianUserInfo` with ToolSearch and collect the distinct prefixes of the matches (everything before `atlassianUserInfo`); also search for `authenticate` and collect the prefixes of Atlassian servers that have it (found, not signed in). Keep the supported ones; mention each unsupported one with the reason (the analyst cannot call it) and do not offer it. For every supported server that is signed in call `atlassianUserInfo` and `getAccessibleAtlassianResources`. Ask which one to use, with one option per server that shows **the signed-in account and its sites, or "not signed in"**, for example "Atlassian Rovo: g@example.com, example.atlassian.net". When a supported server is not signed in, add the option "Sign in with another account (<server>)". The stored `mcpPrefix` is the recommended option when it is signed in and reaches the stored site. Skip the question when exactly one supported server is signed in and nothing else is offered. None at all → tell the user to connect the Atlassian connector at claude.ai, then search again. Call the chosen prefix `P`.
2. **Authorization.** A chosen server that is not signed in: follow "Waiting for an authorization", then continue.
3. **Site.** `getAccessibleAtlassianResources` → `cloudId`, `baseUrl`. The call lists a site once per product (a Jira entry and a Confluence entry with the same `id`): merge entries by `id` first. Several distinct sites → ask which. The chosen site must come from this call made with `P`: that is what binds the repository to a site its connector can reach.
4. **Project and board.** `getVisibleJiraProjects` → ask which project (`projectKey`). Default `boardJql`: `project = <KEY> AND sprint in openSprints()`; let the user change it. It must contain neither an assignee clause nor an `ORDER BY` (the analyst appends its own ordering). Run it once with `searchJiraIssuesUsingJql` (`maxResults` 1) to validate it.
5. **Target user.** Default: the current user from `atlassianUserInfo`. Another person → `lookupJiraAccountId`. Store the **accountId**, never the display name. Verify it before moving on: for the current user it must equal `account_id` from the `atlassianUserInfo` call (same server, same site); for another person run `searchJiraIssuesUsingJql` with `assignee = "<accountId>"` (`maxResults` 1, fields `assignee`) and show the returned `displayName` for the user to confirm. A wrong id otherwise yields an empty queue on every run with no error.
6. **Statuses, issue types, Confluence spaces.** Offer values read from Jira (`getJiraProjectIssueTypesMetadata`; statuses seen on the board) and `getConfluenceSpaces` (`openStatuses`, `issueTypes`, `confluenceSpaces`). `confluenceMaxPages` default 3.
7. **Write mode.** Ask for `writeMode`: `none`, `labels`, `labels+comments`, `labels+comments+transition` (explain that triage writes `agent-*` labels and question comments before any plan checkpoint, and PR status after a PR opens). For transitions, read the real names with `getTransitionsForJiraIssue` on one board ticket and ask for `onHandoff` (optional) and `onPrOpened`.
8. **Save Stage 1.** Merge into `.agentic-workflow/local.json` (`mcpPrefix`, `assigneeAccountId`) and into the `jira` section of `.claude/agentic-workflow.json` (team-shared, may be committed: `cloudId`, `baseUrl`, `projectKey`, `boardJql`, `openStatuses`, `issueTypes`, `confluenceSpaces`, `confluenceMaxPages`, `writeMode`, `transitions`). Add `.agentic-workflow/` to `$(git rev-parse --git-common-dir)/info/exclude`. Ask where the permission rules go (see "Permission rules"), then write: `allow` `P` + `atlassianUserInfo`, `getAccessibleAtlassianResources` (the preflight of every run calls them), `searchJiraIssuesUsingJql`, `getJiraIssue`, `getJiraIssueRemoteIssueLinks`, `getTransitionsForJiraIssue`, `searchConfluenceUsingCql`, `getConfluencePage`, plus the write tools the chosen `writeMode` permits (`editJiraIssue` for labels, `addCommentToJiraIssue` for comments, `transitionJiraIssue` for transitions), and `Bash(wait-mcp *)`; `deny` the write tools that `writeMode` does not permit, so a prompt mistake cannot write. Other tools of the same server stay on the default "ask" behavior (the server also has write tools such as `createJiraIssue`); an organization-level `ask` rule can override `allow`. Print "Jira saved: <baseUrl> / <projectKey> through <mcpPrefix>" and start Stage 2.

## Stage 2: GitHub and repo
Say "Stage 2 of 3: GitHub and repo". Bind this repository to one gh account.
1. **Remote.** `git remote get-url origin` (none → tell the user to add the remote and stop). SSH form `git@<alias>:<owner>/<repo>.git` or `ssh://git@<alias>/<owner>/<repo>.git`: the real host comes from `ssh -G <alias>` (its `hostname` line), because the alias can differ from the host (for example `github.com-personal`). HTTPS form: the host is in the URL. Call the host `H`. `<owner>/<repo>` is the last two path segments without `.git`; parse it, do not ask gh (the active gh account may have no access to a private repository).
2. **Who pushes.** On an SSH remote run `ssh -T -o BatchMode=yes -o ConnectTimeout=8 git@<alias-or-host>`; it answers `Hi <login>!` (a non-zero exit is normal). That login is the expected account. On an HTTPS remote say that pushes use git's credential helper, which is not checked here.
3. **Accounts.** `gh auth status --hostname H --json hosts` lists the logged-in accounts (`login`, `active`, `state`; it has no tokens). Ignore accounts whose `state` is not `success`. For each remaining account X: `gh-as --account X --host H repo view H/<owner>/<repo> --json viewerPermission --jq .viewerPermission`; candidates are `WRITE`, `MAINTAIN` and `ADMIN`, an error means "no access".
4. **Login, when needed.** No account is logged in, or the expected account from step 2 is not among them (it probably has access to the repository), or no candidate exists: first start `wait-gh-login --host H --login <expected login>` with Bash `run_in_background` (omit `--login` when there is no expected login), then give the user exactly one command, `! gh auth login --hostname H` (the `!` runs it in this session), and end the turn. When the watcher ends, run step 3 again; the continuation must be safe to run twice. Add that a new login normally becomes gh's active account on that host, that `gh auth switch --user <previous login>` puts the old one back, and that this workflow does not depend on which account is active. Never say that the login leaves the active account unchanged. If the watcher times out, ask one single-option question "I logged in" and run step 3 again.
5. **Account.** The expected account is the default when it is a candidate. If it is not, warn that pushes go out as `<login>` while pull requests would be opened as the chosen account. Ask the user to confirm the account (one candidate → it is the default, several → they choose). No candidate after step 4 → stop and show every account with its permission, so the user can fix access or log in with another account.
6. **Implementer scope and base branch.** Infer `implementerScope` from the repo (for example an Angular/Nx workspace → `frontend-angular`) and ask for confirmation. Then ask which branch feature branches start from and pull requests target (`baseBranch`): offer the stored value if config exists, otherwise the repository's default (`git symbolic-ref --short refs/remotes/origin/HEAD` without the `origin/` prefix, else the `ref:` line of `git ls-remote --symref origin HEAD`; neither needs gh), and let the user type another one (for example `develop` or `release/1.2`). Check that it exists with `git ls-remote --exit-code --heads origin <branch>`; if not, ask again.
7. **Save Stage 2.** Merge `github` as `{ "host", "account" }` into `.agentic-workflow/local.json`, `baseBranch` at the top level and `jira.implementerScope` into `.claude/agentic-workflow.json`. `<owner>/<repo>` is not stored: every run reads it from `origin`. Write the rules (to the place chosen in Stage 1): `allow` `Bash(gh-as --account <A> --host <H> repo view *)`, `... pr list *`, `... pr view *`, `... pr checks *`, and `Bash(wait-gh-login *)`. A rule matches only a command that begins with exactly this text, so the agents always write `--account` before `--host`, and a command that puts an environment assignment in front of `gh` does not match. Creating or editing a pull request or a comment, and `git push`, stay on the default "ask" behavior. Print "GitHub saved: <H>/<owner>/<repo> as <account> (<permission>), base <baseBranch>" and start Stage 3.

## Stage 3: behavior
Say "Stage 3 of 3: behavior".
1. **Investigation.** Explain that before asking the operator, the analyst looks for answers in the repo and, optionally, in the running app. Code search: `investigation.code`, default yes. Browser (default no): it needs Claude in Chrome. Search for `tabs_context_mcp` with ToolSearch and take the prefix of the match as `browserPrefix` (none found → say Claude in Chrome is not installed or not connected, and leave the browser off). Ask for `appUrl`, which must be a non-production environment (warn if the host looks like production and ask again), and set `allowedOrigins` to its origin. State the limits: read-only navigation, no typing, no login, no form submits, only the allowed origins. Declined → store only `code`.
2. **Operator preferences.** `operatorLanguage` (language for questions and Jira comments), `maxCandidatesPerRun` (default 5).
3. **Save Stage 3.** Merge `operatorLanguage` (and `browserPrefix` when the browser is enabled) into `.agentic-workflow/local.json`, and `maxCandidatesPerRun` and `investigation` into the `jira` section of `.claude/agentic-workflow.json`. Write the rules (to the place chosen in Stage 1): browser enabled: `allow` `browserPrefix` + `tabs_context_mcp`, `tabs_create_mcp`, `tabs_close_mcp`, `navigate`, `get_page_text`, `read_page`, `find`, `computer`, and `deny` `browserPrefix` + `javascript_tool`, `form_input`, `file_upload`, `shortcuts_execute` (`computer` also types and clicks and a permission rule cannot split it: the ban on typing is a rule in the analyst's prompt, so say so). Always: `allow` `Read(~/.claude/agent-memory/**)` and `Edit(~/.claude/agent-memory/**)`. Use `Edit`, not `Write`: file writes are checked against `Edit` rules, a `Write(...)` rule never matches. The `implementer` keeps what it learns about each repository there; without the rules every memory write prompts, and in an unattended or `dontAsk` run it is denied and nothing is saved. The memory is global, so recommend the user-level file; in this repo's `.claude/settings.local.json` the rules apply only here. Print "Behavior saved: language <operatorLanguage>, investigation <code/browser>".

## Finish
Print what is stored and where, one line per stage (the three saved lines, plus the values you took without asking), and say: "Setup is done for this repository and does not need to be repeated. Run `/agentic-workflow:start` (next ticket) or `/agentic-workflow:start ABC-123`. To change something later run `/agentic-workflow:setup` again: it shows the current values and asks what to change (or `--reconfigure jira|github|behavior|permissions` for one part)."

Do not store secrets anywhere, and never print a token. If any step is declined, stop and report what is still missing; do not guess.

# agentic-workflow: setup

You run in the main thread, so you may ask the user. Collect everything the analyst and the publisher will need now, so that `/agentic-workflow:start` never has to ask for configuration or permissions mid-run. Setup is done **once per repository**, **one stage at a time**: Stage 1 Jira, Stage 2 GitHub and repo, Stage 3 behavior. A stage is finished and saved before the next one starts. When the repository is already set up, re-running setup shows the current values and asks what to change.

Arguments: `$ARGUMENTS`

**One stage at a time.** Say which stage you are in ("Stage 1 of 3: Jira") and what you need from the user now. Never mention, list or preview a later stage, and never print a "still to do" list. When a stage is saved, print one line for it and go on to the next stage by yourself.

**Tool names.** Atlassian tools come either from the plugin's own server (prefix `mcp__plugin_agentic-workflow_atlassian__`) or from a claude.ai Atlassian connector (for example `mcp__claude_ai_Atlassian_Rovo__`). Claude Code hides the plugin's server when a connector with the same URL exists, so the prefix differs per user. Stage 1 finds it and stores it as `P` (`mcpPrefix`); from then on call every tool by the exact name `P<tool>`, never by a bare name. Only the prefixes listed under "Supported Atlassian prefixes" in `skills/start/references/config-schema.md` can be used: the analyst's `tools:` allowlist names exactly those.

**GitHub accounts.** Never run `gh auth switch` or anything else that changes gh's active account or its config: other terminals must not notice this workflow. Every gh call goes through the wrapper `gh-as --account <login> --host <host> <gh arguments>` (in this plugin's `bin/`), which gives one process the token of that account. Never print or store a token.

**Where things are stored.** Run `aw-paths` (in this plugin's `bin/`; it prints `key=value` lines, read them and never `eval` them). It gives `host`, `owner`, `repo` (from `origin`), `mode`, and the absolute paths `config` (the active repository config, called `Config` below), `team_config`, `personal_config`, `local` (`Local`: the personal values, always outside the repository), `state` (the run folder) and `legacy`. A failure means no git repository or no usable `origin`: show its message, tell the user to add the remote (`git remote add origin <url>`) if that is what is missing, and stop. The repository config is either **shared with the team** in `<repo>/.claude/agentic-workflow.json` (`team_config`) or kept **only on this computer** in `personal_config`, with nothing written into the repository; the layout and the reasons are in `skills/start/references/config-schema.md` ("Storage"). The Write tool creates missing folders, so the config files need no `mkdir`; the run folder `state` is created by the first run file an agent writes (only the migration, which moves files into it, runs `mkdir -p` for it). Write the config files with the Write or Edit tool in this conversation, never with a shell redirect and never from a subagent: the plugin's guard hook trusts `Config` and `Local`, so Claude Code's permission prompt for these files is the safeguard (it protects as long as prompts are on: a mode that skips them, such as `bypassPermissions`, or a broad shell allow rule removes it for any file), and no permission rule may be added for them. Tell the user so when the first prompt appears. Write arrays of strings (`allowedOrigins`, `acceptedOrigins`) on one line, because the guard reads these files line by line. Merge into an existing file and keep the keys you do not own.

**A team config is shared.** In `team` mode a key that already exists in `Config` was agreed by the team: read it, show it and use it, but do not ask for it again and do not rewrite it. A stage then asks only for what `Config` lacks and for the personal values (Atlassian connector, target user, your own accepted write mode, the gh account, language, consent to the browser). Only creating the file, or an explicit `--reconfigure jira|github|behavior` after a warning that the change goes to everyone who pulls the file, writes shared keys. This keeps your limits (`acceptedWriteMode`, `acceptedOrigins` in `Local`) independent from the team's: you may accept less than the shared file allows and the plugin applies the lower value; you never have to widen the shared file to use the workflow.

## Choose the mode (step 0)
Run `aw-paths`, then read `Config` (when `mode` is `team` or `personal`) and `Local` (a missing file counts as empty), and the table "Setup stages" in `skills/start/references/config-schema.md`, which says which stage owns which required key. Two things come before the table:
- `mode` `conflict` (a team file and a personal file both exist): ask one single-select question, "Keep the team file in the repository" or "Keep the file on this computer", show both `jira.projectKey` and `writeMode` in the question, delete the other file (a tracked team file shows up as an uncommitted deletion: say that the user commits it) and go on.
- "Migration from an older version" (below) when it applies.

A `--reconfigure <part>` argument wins over the table: run that part (`jira` = Stage 1, `github` = Stage 2, `behavior` = Stage 3; `media` = only the pictures step of Stage 3, saved on its own; `storage` = "Moving the configuration" below; `permissions` = run the permission check and write the permission rules again from the stored config). Otherwise take the first row that applies:

| # | Situation | What you do |
|---|---|---|
| 1 | Any required key or file is missing | Run the stages that own the missing keys, in order, skipping a stage whose keys all exist; stored values are the recommended options. This is the normal path for a new repository, for a setup that was interrupted (it continues where it stopped, no progress file is needed) and for a repository set up by an older version of the plugin. Never print a status and stop here. |
| 2 | Every required key exists | Run the checks below, show a short status, then ask one question, screen 0: what to change. A stage whose check failed is run whatever the user answers. |

**Screen 0** (single-select, header `Change`): put the current values in the question text, for example "Jira <baseUrl> / <projectKey> through <mcpPrefix>; GitHub <host>/<owner>/<repo> as <account>; write mode <writeMode>; configuration <shared with the team in the repository | only on this computer>. What do you want to change?". Options: Jira / GitHub and repo / Behavior / Nothing. When a stage is done, ask "Anything else?" with the same options. "Nothing" ends with the summary. The screen is single-select on purpose: "Nothing" is ambiguous next to other choices in a multi-select. Moving the configuration is reached with `--reconfigure storage`; name it in the status line. Picture analysis belongs to Behavior; show "pictures on|off" in the status and name `--reconfigure media`.

**Guard.** A plain run that reaches the end without writing anything, and where the user did not choose "Nothing" on screen 0, skipped its questions: go back and ask them.

Checks (run in row 2; the stage in brackets is run when the check fails):
1. [Stage 1] `mcpPrefix` is a supported prefix, `P` + `atlassianUserInfo` succeeds, and `jira.cloudId` is among the sites `getAccessibleAtlassianResources` returns for `P`.
2. [Stage 1] `assigneeAccountId` (in `Local`) is set. A value that differs from the authenticated account is allowed (another person), but note it.
3. [Stage 1] `acceptedWriteMode` (in `Local`) is set. When `jira.writeMode` of `Config` is wider than it (a teammate raised the shared file, or you deliberately accepted less), that is not a failure: say in the status "the config allows X, your limit is Y, Y applies" and mention `--reconfigure jira` for accepting more.
4. [Stage 3] When `Config` configures the browser (`jira.investigation.browser`) but `Local` has no `browserPrefix` or no `acceptedOrigins`, the user never consented: the browser stays off, so run Stage 3 and ask. Configured origins that are missing from `acceptedOrigins` are only noted in the status (the browser works on the overlap).
5. [Stage 2] `Local` has `github.host` and `github.account`, `gh auth status --hostname <host> --json hosts` lists that account with `state` `success`, and `gh-as --account <account> --host <host> repo view <host>/<owner>/<repo> --json viewerPermission` returns `WRITE`, `MAINTAIN` or `ADMIN` (`<owner>/<repo>` from `aw-paths`).
6. [permission rules] The rules each stage writes exist for the **current** `mcpPrefix` and the current GitHub account in the user's `~/.claude/settings.json`. Rules that exist only for another prefix, or only in this repo's `.claude/settings.local.json` (older versions), do not count. Write the missing ones.
7. [stale rules] Older versions wrote rules that now do harm: see "Migration from an older version", item 2. Offer to remove them.
8. [pictures step of Stage 3] `Local` has `media.email`: `jira-attachment check --email <email> --site <host of jira.baseUrl>` (with `--cloud-id <jira.cloudId>` when `media.gateway` is true) must print `ok <accountId>`. Exit 3 (the token is gone from the keychain) or 4 (expired or revoked) is a failure: run only the pictures step. When `jira.media.enabled` is true but `Local` has no `media.email`, the shared file switches pictures on and you never set them up: run the pictures step and ask. `media-prep check` printing `ffmpeg no` is only noted in the status (screenshots work, recordings do not).

## How to ask
Make setup as easy as possible for the user:
- **Detect inside the stage, ask second.** A stage starts with its own detection and then asks. Stage 1 detects the connectors, their signed-in accounts and sites, the projects, issue types and statuses; Stage 2 the host and `<owner>/<repo>` of `origin`, the logged-in gh accounts with their permission, the SSH identity, the default branch and the inferred `implementerScope`. Do not detect for a later stage. Skip every question that has only one possible answer and name that value in the stage's saved line.
- **Group a stage's questions into a few screens**, one `AskUserQuestion` call each (at most 4 questions per call, 2-4 options per question, headers of at most 12 characters).
- **First option = the detected or stored value, marked "(Recommended)"**, so that confirming it is enough. Other values come through "Other".
- **Put values in the question and option text.** The dialog can hide text printed above it, so a status line before a screen is not enough.
- **Lists longer than 4** (projects, statuses, issue types, spaces): propose one set and ask "use these / change"; show the full list only on "change".
- **Never accept automatically:** `writeMode`, browser investigation, picture analysis and the storage choice. Mark a `writeMode` "(Recommended)" only when it is the stored (accepted) value; mark neither storage option.
- **Prepare everything you can, so the user only clicks.** An authorization is a link that setup waits on (next section), never a list of instructions. The only thing left as a command is `gh auth login`, which is interactive (the Atlassian API token for pictures is stored by setup itself from the clipboard, Stage 3).
- **No separate "save?" click.** The values were chosen on the screens; the stage saves itself when its last screen is answered.

## Waiting for an authorization
Used by Stage 1 for the Atlassian server and by the `start` preflight. The server's name for `wait-mcp` is the one `claude mcp list` prints: `plugin:agentic-workflow:atlassian` for the prefix `mcp__plugin_agentic-workflow_atlassian__`, and `claude.ai <Name with spaces>` for `mcp__claude_ai_<Name>__`. A server that is not signed in exposes only `<prefix>authenticate` and `<prefix>complete_authentication` instead of its real tools. In one turn, in this order:
1. `wait-mcp --check <server>`. Exit 0: it is already connected, search for its real tools and go on. Exit 2: the CLI does not know that name, so do not wait on it; use the one-click question of step 6. Exit 1: it needs authorization, go on.
2. Search for the server's name once first (a sign-in that is still held reconnects by itself).
3. Say in one line that you will wait for the approval in the background and that Claude Code may ask once to allow that command. Start `wait-mcp <server>` with Bash `run_in_background`.
4. Call `<prefix>authenticate`: it returns an authorization URL. If the user declines the call, do not call it again; tell them to run `/mcp` instead.
5. End the turn with the link as the last text, so that no permission dialog covers it: one clickable Markdown link on its own line, one short sentence ("Open this link, choose the Atlassian account that has your project and click Accept; I continue by myself"), and one more line: if the browser ends on a `http://localhost:<port>/callback?code=…` page that does not load (a link opened on another device), paste that address here. Pass a pasted address to `<prefix>complete_authentication` as `callback_url`.
6. When `wait-mcp` ends with exit 0, search for the real tools again (`atlassianUserInfo`), retrying a few times, and continue. If `wait-mcp` timed out (exit 1) or the tools are still missing, ask one single-option question "I approved the link", then search again; if they are still missing, show the link once more, and only then point to `/mcp`.
7. The continuation must be safe to run twice: if the user writes while you wait, and the real tools already exist, go straight on; never call `authenticate` twice for one link.
Claude Code or claude.ai stores and refreshes the token; do not try to read tokens or cookies from the browser.

## Permission rules
Each stage writes its own rules when it saves. There is no question about where: **all rules go to the user's `~/.claude/settings.json`** (create it as `{}` when missing; merge into `permissions.allow`, never overwrite, add only what is missing), because every rule is identical across repositories, so the file can hold the rules of every repository you set up without conflict (a gh account or prefix used only by another repository is just an unused `allow` rule).

Only `allow` rules, and only for what is the same everywhere or per run: the read tools of Jira, the wait scripts, `aw-paths`, `aw-decisions` (it only reads and appends the answer history in the run folder), read-only `gh-as` commands, the picture scripts (`jira-attachment get|check`, `media-prep`), the run files and the implementer's memory. **Never write a `deny` rule, a rule for a Jira write tool or a browser rule.** A `deny` at user level beats every `allow` at every level and would block other repositories and unrelated sessions; what the analyst may write to Jira or do in the browser is decided per repository by the plugin's guard hook from `writeMode` and the browser settings. The `Edit` rule covers the run-file tree `state/` only (see Stage 1), never `local.json` or `config.json`. Print the exact rules in the stage's saved line so the user sees what was added.

## Migration from an older version
Run this once, before the stages, when it applies; ask each question once.
1. **Run files and settings in the repository.** `legacy` (the repository's `.agentic-workflow/` folder) exists. If it holds a `local.json` and `Local` does not exist yet, use its values as the recommended answers of the stages and remove that `local.json` after Stage 1 saved them. If it holds run files (`ledger.json`, `lock.json`, `last_run.json`, `pending/`, ticket folders), ask one single-select question: "Move the run files to <state> (Recommended)" or "Leave them". Moving is `mv` of each entry to `state` (`mkdir -p` first) except `local.json`, skipping an entry that already exists there and saying so; remove the legacy folder with `rmdir` when it is empty and tell the user when it is not. Mention that `.git/info/exclude` still lists `.agentic-workflow/` and that this is harmless.
2. **Rules that now do harm.** Read `permissions.allow` and `permissions.deny` in `~/.claude/settings.json` and in this repo's `.claude/settings.local.json`. Find every rule for `editJiraIssue`, `addCommentToJiraIssue` or `transitionJiraIssue` with any supported Atlassian prefix, and every rule that starts with `mcp__claude-in-chrome__`. Older versions wrote them: a user-level `deny` blocks these tools in every repository and session, and a user-level browser `allow` opens the browser everywhere. Show the exact list and ask one single-select question: "Remove them (Recommended)" or "Keep them". Say before asking that rules the user added on their own for other reasons are in this list too, and that the plugin does not need any of them. Remove only the listed entries, with the Edit tool. On "Keep", warn that a remaining `deny` for a write tool also blocks the analyst when `writeMode` allows it.
3. **Storage.** A repository set up by an older version has its config in `<repo>/.claude/agentic-workflow.json`, so `mode` is `team`. Do not move it silently; say in the Stage 1 line that it stays shared and that `/agentic-workflow:setup --reconfigure storage` keeps it on this computer only.

## Moving the configuration (`--reconfigure storage`)
Show where it is now (`mode`) and ask one single-select question: move it to the other place or leave it.
- **team → personal:** write `Config` to `personal_config` (same content), then delete the repository's `.claude/agentic-workflow.json`. If git tracks it, tell the user the deletion is uncommitted and they commit it. Nothing else changes: `Local` and `state` do not move.
- **personal → team:** write `Config` to `team_config` (create `.claude/`), delete `personal_config`, and tell the user to commit the file if they want to share it, and that teammates still choose their own limits in their own setup.
Never leave both files in place (that is a `conflict`). `Local` and the accepted limits are untouched.

## Stage 1: Jira
Say "Stage 1 of 3: Jira".
1. **Storage.** `mode` `none` (a new repository): ask one single-select question, header `Storage`, with no option marked "(Recommended)": "Only on this computer" (the configuration, the personal values and the run files go to `~/.claude/agentic-workflow/…`; nothing is written into the repository, which suits a workflow that is adapted to you alone) or "In the repository, shared with the team" (creates `.claude/agentic-workflow.json`, which you may commit so teammates start from the same project settings; each teammate still runs their own setup and the plugin never lets a changed shared file widen what you accepted). The answer decides where `Config` is written: `personal_config` or `team_config`. For `mode` `team` or `personal` the place is already decided; name it in the stage's saved line.
2. **Atlassian server.** Search for `atlassianUserInfo` with ToolSearch and collect the distinct prefixes of the matches (everything before `atlassianUserInfo`); also search for `authenticate` and collect the prefixes of Atlassian servers that have it (found, not signed in). Keep the supported ones; mention each unsupported one with the reason (the analyst cannot call it) and do not offer it. For every supported server that is signed in call `atlassianUserInfo` and `getAccessibleAtlassianResources`. Ask which one to use, with one option per server that shows **the signed-in account and its sites, or "not signed in"**, for example "Atlassian Rovo: g@example.com, example.atlassian.net". When a supported server is not signed in, add the option "Sign in with another account (<server>)". The stored `mcpPrefix` is the recommended option when it is signed in and reaches the stored site. Skip the question when exactly one supported server is signed in and nothing else is offered. None at all → tell the user to connect the Atlassian connector at claude.ai, then search again. Call the chosen prefix `P`.
3. **Authorization.** A chosen server that is not signed in: follow "Waiting for an authorization", then continue.
4. **Site.** `getAccessibleAtlassianResources` → `cloudId`, `baseUrl`. The call lists a site once per product (a Jira entry and a Confluence entry with the same `id`): merge entries by `id` first. Several distinct sites → ask which. The chosen site must come from this call made with `P`: that is what binds the repository to a site its connector can reach.
5. **Project and board.** `getVisibleJiraProjects` → ask which project (`projectKey`). Default `boardJql`: `project = <KEY> AND sprint in openSprints()`; let the user change it. It must contain neither an assignee clause nor an `ORDER BY` (the analyst appends its own ordering). Run it once with `searchJiraIssuesUsingJql` (`maxResults` 1) to validate it.
6. **Target user.** Default: the current user from `atlassianUserInfo`. Another person → `lookupJiraAccountId`. Store the **accountId**, never the display name. Verify it before moving on: for the current user it must equal `account_id` from the `atlassianUserInfo` call (same server, same site); for another person run `searchJiraIssuesUsingJql` with `assignee = "<accountId>"` (`maxResults` 1, fields `assignee`) and show the returned `displayName` for the user to confirm. A wrong id otherwise yields an empty queue on every run with no error.
7. **Statuses, issue types, Confluence spaces.** Offer values read from Jira (`getJiraProjectIssueTypesMetadata`; statuses seen on the board) and `getConfluenceSpaces` (`openStatuses`, `issueTypes`, `confluenceSpaces`). `confluenceMaxPages` default 3.
8. **Write mode.** Ask for `writeMode`: `none`, `labels`, `labels+comments`, `labels+comments+transition` (explain that triage writes `agent-*` labels and question comments before any plan checkpoint, and PR status after a PR opens, and that the plugin's guard enforces the chosen mode for this repository only). This answer is the user's own limit, `acceptedWriteMode`; the effective mode of a run is the lower of it and `jira.writeMode`. The recommended option is the stored `acceptedWriteMode`, never a value found in a shared config: when `Config` already has `jira.writeMode` (team mode), put it in the question text ("the team file says X"), mark nothing as recommended unless a limit is already stored, and do not rewrite the shared value. For transitions, read the real names with `getTransitionsForJiraIssue` on one board ticket and ask for `onHandoff` (optional) and `onPrOpened`.
9. **Save Stage 1.** Merge into `Local` (`mcpPrefix`, `assigneeAccountId`, `acceptedWriteMode` = the chosen `writeMode`) and into the `jira` section of `Config` (`cloudId`, `baseUrl`, `projectKey`, `boardJql`, `openStatuses`, `issueTypes`, `confluenceSpaces`, `confluenceMaxPages`, `writeMode`, `transitions`; in team mode this file may be committed, so write only the keys it lacks, or all of them on `--reconfigure jira`). Then write the rules to `~/.claude/settings.json`, all `allow`: `P` + `atlassianUserInfo`, `getAccessibleAtlassianResources` (the preflight of every run calls them), `searchJiraIssuesUsingJql`, `getJiraIssue`, `getJiraIssueRemoteIssueLinks`, `getTransitionsForJiraIssue`, `searchConfluenceUsingCql`, `getConfluencePage`; `Bash(wait-mcp *)`, `Bash(aw-paths)`, `Bash(aw-paths *)`, `Bash(aw-decisions *)`; and for the run files `Read(~/.claude/agentic-workflow/**)` and `Edit(~/.claude/agentic-workflow/state/**)` (use `Edit`, not `Write`: file writes are checked against `Edit` rules; the run files have a tree of their own, so the pattern can never match `local.json` or `config.json`). Do not write any rule for `editJiraIssue`, `addCommentToJiraIssue` or `transitionJiraIssue`: the guard allows them inside `writeMode`, and without it they keep asking. Other tools of the same server stay on the default "ask" behavior (the server also has write tools such as `createJiraIssue`); an organization-level `ask` rule can override `allow`. Print "Jira saved: <baseUrl> / <projectKey> through <mcpPrefix>, write mode <writeMode>, configuration <shared in the repository | only on this computer>" and start Stage 2.

## Stage 2: GitHub and repo
Say "Stage 2 of 3: GitHub and repo". Bind this repository to one gh account.
1. **Remote.** `host` (call it `H`), `owner` and `repo` come from `aw-paths`; it resolved an SSH alias (for example `github.com-personal`) to the real host with `ssh -G`, and parsed `<owner>/<repo>` from `origin` (do not ask gh: the active gh account may have no access to a private repository). The alias itself, needed only in step 2, is the host part of `git remote get-url origin` (`git@<alias>:<owner>/<repo>.git` or `ssh://git@<alias>/<owner>/<repo>.git`).
2. **Who pushes.** On an SSH remote run `ssh -T -o BatchMode=yes -o ConnectTimeout=8 git@<alias-or-host>`; it answers `Hi <login>!` (a non-zero exit is normal). That login is the expected account. On an HTTPS remote say that pushes use git's credential helper, which is not checked here.
3. **Accounts.** `gh auth status --hostname H --json hosts` lists the logged-in accounts (`login`, `active`, `state`; it has no tokens). Ignore accounts whose `state` is not `success`. For each remaining account X: `gh-as --account X --host H repo view H/<owner>/<repo> --json viewerPermission --jq .viewerPermission`; candidates are `WRITE`, `MAINTAIN` and `ADMIN`, an error means "no access".
4. **Login, when needed.** No account is logged in, or the expected account from step 2 is not among them (it probably has access to the repository), or no candidate exists: first start `wait-gh-login --host H --login <expected login>` with Bash `run_in_background` (omit `--login` when there is no expected login), then give the user exactly one command, `! gh auth login --hostname H` (the `!` runs it in this session), and end the turn. When the watcher ends, run step 3 again; the continuation must be safe to run twice. Add that a new login normally becomes gh's active account on that host, that `gh auth switch --user <previous login>` puts the old one back, and that this workflow does not depend on which account is active. Never say that the login leaves the active account unchanged. If the watcher times out, ask one single-option question "I logged in" and run step 3 again.
5. **Account.** The expected account is the default when it is a candidate. If it is not, warn that pushes go out as `<login>` while pull requests would be opened as the chosen account. Ask the user to confirm the account (one candidate → it is the default, several → they choose). No candidate after step 4 → stop and show every account with its permission, so the user can fix access or log in with another account.
6. **Implementer scope and base branch.** Infer `implementerScope` from the repo (for example an Angular/Nx workspace → `frontend-angular`) and ask for confirmation. Then ask which branch feature branches start from and pull requests target (`baseBranch`): offer the stored value if config exists, otherwise the repository's default (`git symbolic-ref --short refs/remotes/origin/HEAD` without the `origin/` prefix, else the `ref:` line of `git ls-remote --symref origin HEAD`; neither needs gh), and let the user type another one (for example `develop` or `release/1.2`). Check that it exists with `git ls-remote --exit-code --heads origin <branch>`; if not, ask again.
7. **Save Stage 2.** Merge `github` as `{ "host", "account" }` into `Local`, `baseBranch` at the top level and `jira.implementerScope` into `Config` (in team mode only the keys it lacks, or on `--reconfigure github`). `<owner>/<repo>` is not stored: every run reads it from `origin`. Write the rules to `~/.claude/settings.json`: `allow` `Bash(gh-as --account <A> --host <H> repo view *)`, `... pr list *`, `... pr view *`, `... pr checks *`, and `Bash(wait-gh-login *)`. A rule matches only a command that begins with exactly this text, so the agents always write `--account` before `--host`, and a command that puts an environment assignment in front of `gh` does not match. Creating or editing a pull request or a comment, and `git push`, stay on the default "ask" behavior. Print "GitHub saved: <H>/<owner>/<repo> as <account> (<permission>), base <baseBranch>" and start Stage 3.

## Stage 3: behavior
Say "Stage 3 of 3: behavior".
1. **Investigation.** Explain that before asking the operator, the analyst looks for answers in the repo and, optionally, in the running app. Code search: `investigation.code`, default yes. Browser (default no): it needs Claude in Chrome. Search for `tabs_context_mcp` with ToolSearch and take the prefix of the match as `browserPrefix` (none found → say Claude in Chrome is not installed or not connected, and leave the browser off; the plugin can use only the prefix `mcp__claude-in-chrome__`). Ask for `appUrl`, which must be a non-production environment (warn if the host looks like production and ask again), and set `allowedOrigins` to its origin. State the limits: read-only navigation, no typing, no login, no form submits, only the allowed origins, and that the guard allows the analyst only the read tools `tabs_context_mcp`, `tabs_create_mcp`, `tabs_close_mcp`, `navigate`, `get_page_text`, `read_page`, `find` and `computer`, only for this repository. Declined → store only `code`, and remove `browserPrefix`, `acceptedOrigins` and `investigation.browser` if an earlier setup stored them.
2. **Operator preferences.** `operatorLanguage` (language for questions and Jira comments), `maxCandidatesPerRun` (default 5).

# agentic-workflow: setup

You run in the main thread, so you may ask the user. Collect everything the analyst will need now, so that `/agentic-workflow:start` never has to ask for configuration or permissions mid-run. This skill is idempotent: when config already exists, offer the stored values as defaults.

**Tool names.** Atlassian tools come either from the plugin's own server (prefix `mcp__plugin_agentic-workflow_atlassian__`) or from a claude.ai Atlassian connector (for example `mcp__claude_ai_Atlassian_Rovo__`). Claude Code hides the plugin's server when a connector with the same URL exists, so the prefix differs per user. Step 1 finds it and stores it as `P` (`mcpPrefix`); from then on call every tool by the exact name `P<tool>`, never by a bare name.

## Steps
1. **Atlassian server and authorization.**
   - Find the server: search for `atlassianUserInfo` with ToolSearch and collect the distinct prefixes of the matches (everything before `atlassianUserInfo`). One prefix → use it. Several (two connectors, or the plugin server and a connector) → ask which one to use. None → tell the user to connect the Atlassian connector at claude.ai, or to run `/mcp` → `plugin:agentic-workflow:atlassian` → Authenticate (this works only when no connector has the same URL), then search again.
   - Call `P` + `atlassianUserInfo`. If it fails or returns 401, tell the user to run `/mcp`, choose that server, pick Authenticate (a browser opens, sign in to Atlassian), then reply "done". Retry at most twice; then stop and repeat the instruction. Claude Code or claude.ai stores and refreshes the token; do not try to read tokens or cookies from the browser.
2. **Site.** `getAccessibleAtlassianResources` → `cloudId`, `baseUrl`. The call lists a site once per product (a Jira entry and a Confluence entry with the same `id`): merge entries by `id` first. Several distinct sites → ask which.
3. **Project and board.** `getVisibleJiraProjects` → ask which project (`projectKey`). Default `boardJql`: `project = <KEY> AND sprint in openSprints()`; let the user change it. It must contain neither an assignee clause nor an `ORDER BY` (the analyst appends its own ordering). Run it once with `searchJiraIssuesUsingJql` (`maxResults` 1) to validate it.
4. **Target user.** Default: the current user from `atlassianUserInfo`. Another person → `lookupJiraAccountId`. Store the **accountId**, never the display name. Verify it before moving on: for the current user it must equal `account_id` from the `atlassianUserInfo` call of step 1 (same server, same site); for another person run `searchJiraIssuesUsingJql` with `assignee = "<accountId>"` (`maxResults` 1, fields `assignee`) and show the returned `displayName` for the user to confirm. A wrong id otherwise yields an empty queue on every run with no error.
5. **Statuses, issue types, Confluence spaces.** Offer values read from Jira (`getJiraProjectIssueTypesMetadata`; statuses seen on the board) and `getConfluenceSpaces` as multi-select questions (`openStatuses`, `issueTypes`, `confluenceSpaces`). `confluenceMaxPages` default 3.
6. **implementerScope.** Infer from the repo (for example an Angular/Nx workspace → `frontend-angular`) and ask for confirmation.
7. **Investigation.** Explain that before asking the operator, the analyst looks for answers in the repo and, optionally, in the running app. Code search: `investigation.code`, default yes. Browser (default no): it needs Claude in Chrome. Search for `tabs_context_mcp` with ToolSearch and take the prefix of the match as `browserPrefix` (none found → say Claude in Chrome is not installed or not connected, and leave the browser off). Ask for `appUrl`, which must be a non-production environment (warn if the host looks like production and ask again), and set `allowedOrigins` to its origin. State the limits: read-only navigation, no typing, no login, no form submits, only the allowed origins. Declined → store only `code`.
8. **Write permissions.** Ask for `writeMode`: `none`, `labels`, `labels+comments`, `labels+comments+transition` (explain that triage writes `agent-*` labels and question comments before any plan checkpoint, and PR status after a PR opens). For transitions, read the real names with `getTransitionsForJiraIssue` on one board ticket and ask for `onHandoff` (optional) and `onPrOpened`.
9. **Operator preferences.** `operatorLanguage` (language for questions and Jira comments), `maxCandidatesPerRun` (default 5).
10. **Write config** (merge, keep unrelated keys): the `jira` section of `.claude/agentic-workflow.json` (team-shared, may be committed; includes `investigation`) and `.agentic-workflow/local.json` (`assigneeAccountId`, `operatorLanguage`, `mcpPrefix`, and `browserPrefix` when the browser is enabled). Add `.agentic-workflow/` to `$(git rev-parse --git-common-dir)/info/exclude`.
11. **Permissions.** Show the exact rules, then ask where to write them: user level `~/.claude/settings.json` (the server is identical across repos) or this repo's `.claude/settings.local.json`. Merge into `permissions`, never overwrite:
    - `allow`: `P` + `searchJiraIssuesUsingJql`, `getJiraIssue`, `getJiraIssueRemoteIssueLinks`, `getTransitionsForJiraIssue`, `searchConfluenceUsingCql`, `getConfluencePage`, plus the write tools the chosen `writeMode` permits (`editJiraIssue` for labels, `addCommentToJiraIssue` for comments, `transitionJiraIssue` for transitions).
    - `deny`: the write tools that `writeMode` does not permit, so a prompt mistake cannot write.
    - Browser enabled: `allow` `browserPrefix` + `tabs_context_mcp`, `tabs_create_mcp`, `tabs_close_mcp`, `navigate`, `get_page_text`, `read_page`, `find`, `computer`; `deny` `browserPrefix` + `javascript_tool`, `form_input`, `file_upload`, `shortcuts_execute`. `computer` also types and clicks and a permission rule cannot split it: the ban on typing is a rule in the analyst's prompt, so say so when showing the rules.
    - Implementer memory (always): `allow` `Read(~/.claude/agent-memory/**)` and `Edit(~/.claude/agent-memory/**)`. Use `Edit`, not `Write`: file writes are checked against `Edit` rules, a `Write(...)` rule never matches. The `implementer` keeps what it learns about each repository there; without the rules every memory write prompts, and in an unattended or `dontAsk` run it is denied and nothing is saved. The memory is global, so recommend the user-level file; in this repo's `.claude/settings.local.json` the rules apply only here.
    The Jira and browser rules use the chosen prefix `P` (the memory rules do not). Other tools of the same server stay on the default "ask" behavior (the server also has write tools such as `createJiraIssue`); an organization-level `ask` rule can override `allow`.
    Write only after the user agrees.
12. **Summary.** Print what was stored and where, and say: "Run `/agentic-workflow:start` (next ticket) or `/agentic-workflow:start ABC-123`."

Do not store secrets anywhere. If any step is declined, stop and report what is still missing; do not guess.
